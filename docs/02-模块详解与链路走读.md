# 第 3 章 模块详解

> 按目录逐一拆解每个模块的职责、关键组件与数据流。

## 3.1 collectors/ —— 采集层

### 3.1.1 base.py —— 采集契约

- `CollectionResult`：单个信源一次采集的不可变结果（文章、警告、状态、HTTP 状态、抓取/跳过数、错误码）。
- `LiveCollectionResult`：一次雷达采集的合并结果（含 7/30 天窗口、扩窗分类、逐源计数、SourceRun 列表）。
- `SourceCollector` / `LiveCollector`：协议，定义采集器必须实现 `collect(since, now)`。
- `failed_collection_result()`：把异常归类为稳定错误码（`http_429`/`http_timeout`/`parse_error`/`network_error`/`collector_error`），**不泄漏请求细节**。
- `merge_by_url()`：按 canonical URL 去重，**直接采集器优先于 AIHOT 聚合**，同源取最新。

### 3.1.2 具体采集器

| 采集器 | 数据源 | 特点 |
|---|---|---|
| `rss.py:OfficialFeedCollector` | 官方 RSS/Atom | 解析 item/entry，`relevance_keywords` 可做关键词过滤 |
| `github_releases.py:GitHubReleaseCollector` | GitHub Releases API | 只抓稳定 release，过滤 draft/prerelease/nightly/alpha/beta/rc |
| `hacker_news.py:HackerNewsCollector` | 官方 Firebase API | 按 AI 关键词 + min_points=20 过滤 |
| `bing_wechat.py:BingWeChatCollector` | Bing 公开搜索索引 | 只做公众号文章「线索发现」，`signal_only=True`，T2 |
| `aihot.py:AihotCollector` | aihot.news 公开 JSON | 外部发现通道，走本地 pre-screen/scoring，官方/直连版本优先 |
| `http.py` | — | `HttpGetter` + `RetryingHttpGetter`（重试 3 次，指数退避，仅 429/5xx）+ `build_http_client` |

### 3.1.3 registry.py —— 采集器 → 信源种子

- `sources_from_live_collector()`：把采集器对象转成确定性 `Source` 种子记录。
- `apply_source_registry_state()`：让**持久化的操作员设置（enable/tier/schedule）控制实时执行**——种子刷新不会覆盖人工禁用、tier 修订或健康状态。

### 3.1.4 live.py —— 雷达采集编排

`LiveRadarCollector`：8 线程并行跑所有启用采集器，先 7 天窗口，`_short_categories()` 判断哪类不足 5 条，再对这些类的采集器扩到 30 天窗口。

## 3.2 domain/ —— 领域层

- `models.py`：所有框架无关的领域数据模型（`ArticleRecord`、`CurationDecision`、`HeatScore`、`EvidencePack`、`CreatorProject`、`DraftVersion`、`Source`、`SourceRun`、`DailyReport` 等），用 Pydantic 做校验。**时间字段强制 timezone-aware**。
- `ports.py`：用 `Protocol` 定义 10+ 个仓库接口（`ArticleRepository`、`CurationDecisionRepository`、`SourceRepository`…），业务层只依赖这些协议。
- `relevance.py`：AI 相关性守卫。`is_distribution_eligible()` 只对「已知混合主题源」（IT之家、少数派）要求标题含 AI 关键词，其余源整体信任。
- `fingerprints.py`：`article_content_fingerprint()` = sha256(json{title, summary})，用于增量过滤。
- `sync.py`：精选镜像同步协议（见 §3.8）。

## 3.3 scoring/ —— 评分层

- `heat.py:score_articles()`：四维加权评分。LLM 打分三维 + tier 给 authority；无 LLM 走确定性回退。
- `curation.py`：**代码拥有的精选决策**。`select_curated()` 按门槛 + 容量选精选；`get_quality_adjustment()` 标题质量微调；`explain_curation()` 生成可读推荐理由。
- `classify_summarize.py`：LLM 分类（五分类）+ 中文摘要生成。
- `pre_screen.py`：两段式 AI 预筛，过滤纯营销/PR/无关科技新闻。
- `llm_guard.py`：LLM 调用守卫——每日调用预算、401/402 熔断、跨天重置。

## 3.4 topics/ —— 选题层

- `dedup.py`：`canonicalize_url()` 去掉 tracking 参数（utm_*/fbclid 等），`deduplicate()` 按 URL 再按归一化标题去重。
- `select.py:select_topics()`：按分类取 Top N 候选（每类 5），不足 5 记录 shortage（真实缺口）。
- `classify.py`：显式确定性的选题分类（工具 TOOL / 热点 NEWS）。

## 3.5 services/ —— 服务层

- `pipeline.py:ContentPipeline`：分发流水线核心（见 §2.3）。
- `scheduler.py:CollectionScheduler`：轻量轮询器，每分钟问服务「哪些源到期」，实际执行由持久化 `next_run_at` + 租约决定。
- `source_network.py:SourceNetworkCoordinator`：批量级网络协调，全局断网 vs 单源故障分离。
- `daily.py`：日报生成，按 Asia/Shanghai 自然日分桶，内容哈希幂等，变化才产生新 revision。
- `reliability.py`：信源可靠性报告，滚动 7 日窗口算成功率、样本量、目标值。

## 3.6 evidence/ —— 证据层

`build.py:build_evidence_pack()` 把文章摘要归并成 `EvidencePack`：

- 按句号切分摘要为句子 → 归一化 → 按归一化文本分组 → 每组生成一条 `EvidenceFact`（记录来源、数字、日期、版本号）。
- **事实状态判定**：一条 fact 必须**同时**满足 4 条才算 `verified`：①可被结构化数值正则解析；②不在冲突集；③跨 ≥2 个不同发布者；④至少一个官方/一手且已核验来源。否则 `unverified`；同一主体出现不同数值则 `conflicting`。
- `ready_for_draft = 有 fact 且无冲突且无待核实`。

## 3.7 writing/ —— 创作层

- `provider.py`：`LlmDraftProvider`（AI 三阶段成文 + 审计）与 `RuleBasedDraftProvider`（零依赖兜底）。三阶段：`outline → section → editor`。
- `workflow.py`：确定性创作策略（机会评分、草稿版本构建、质检报告）。
- `quality.py:check_quality()`：8 类质量检查，区分 blocking / 非 blocking。
- `brief.py`：Content Brief 构建 + 证据门。
- `originality.py`：normalized-char-12gram 原创性检测（对主灵感硬门 10%）。
- `inspiration.py`：安全抓取/解析公开 URL（SSRF 拦截），做版权安全的结构分析。
- `export.py`：微信富文本（内联样式 HTML）导出。

## 3.8 storage/ —— 存储层

- `sqlite.py`：主存储（SQLAlchemy Core，手写 `Table` + SQL）。见第 5 章。
- `story_sqlite.py`：Story 影子表。
- `memory.py`：内存降级实现（测试/demo 用）。
- `mongo.py`：MongoDB 分支（motor），功能不完整（缺 Source/SourceRun/DailyReport/Story/Evaluation）。

## 3.9 story/ —— Story 影子引擎

**定位**：一个**零 token 的确定性「旁路投影」**——在正式采集/审核之后运行，写独立的 story 表，只投影不参与分发，失败只记一条 `failed` run 并静默跳过，**不回滚采集、不影响精选/热榜/日报/创作机会**。

**流程**：读近 7 天语料 → 过滤「公开品类 + 已审核且 eligible」→ `recall_candidate_pairs` 用 6 个倒排索引召回候选对 → 并查集聚类 → `_reconcile` 对账 → `apply_batch` 持久化。

**确定性保证**：`st_` 稳定公开标识、增量指纹、合并/拆分谱系、revision 内容哈希。当前 `public_cutover_enabled: False` 锁定，尚未切换到正式线。

## 3.10 evaluation/ —— 评估工作台

- `workbench.py`：人工 R1 标注台，分层轮询补足 200 条候选。
- `replay.py`：用确定性策略对金标重放打分，量化策略与人工一致性（precision/recall/F1）。
- `release_gate.py`：上线硬闸门，聚合源可靠性 + 金标回放，缺一即 blocked。

## 3.11 agent/ —— Agent 层（M2）

- `graph.py`：LangGraph `StateGraph` 实现 decide→execute 循环。
- `tools.py`：4 个本地研究工具 + 参数校验 + 观测边界。
- `model.py`：原生 function calling 封装（不冒充规则）。
- `config.py`：Agent 边界配置（步数/工具次数/超时）。
- `integrations/aihot.py`：外部 AIHOT 资讯发现工具扩展。

## 3.12 api/ —— API 层

- `routes.py`：内部 `/api` 路由 + `ContentApiService`（编排采集→流水线→任务）。
- `v1_routes.py`：公开稳定 `/api/v1` 端点（items/hot-topics/dailies/selected/fingerprint/creation/agent 等）。
- `errors.py`：Problem JSON 错误协议。
- `feeds.py`：RSS 2.0 输出（feed.xml/all.xml/daily.xml/category.xml）。
- `observability.py`：进程内 HTTP 观测（记录 → 聚合）。
- `public_openapi.py`：裁剪出公开 OpenAPI v1 文档（白名单 8 个 GET 端点）。
- `public_schemas.py`：公开 v1 契约的 Pydantic schema。
- `agent.py`：Agent REST 端点（runs/conversations）。
- `story_shadow.py`：Story 影子诊断端点。

## 3.13 web/ —— 前端

React + TypeScript + Vite，页面包括：首页、精选流、全部动态、热榜、五分类、日报、内容机会、创作工作台、评估工作台、Agent 对话等。生产构建输出到 `web/dist`，由 FastAPI 的 `StaticFiles` 直接托管（`main.py:384`）。

# 第 4 章 关键链路走读

## 4.1 一篇 GitHub Release 的精选之旅

以 `google-gemini/gemini-cli` 发布 stable release `v1.0.0` 为例。

**阶段 0 · 采集器定义**（`collectors/defaults.py:51`）：`GitHubReleaseCollector(..., tier=T1, category=AI_PRODUCTS, limit=10)`。`feed_url` = Releases API，`schedule_minutes` = 10（T1）。

**阶段 1 · 调度触发**：APScheduler 每分钟 `_do_collect` → `create_scheduled_live_task()` → `_claim_source_ids()`（`SourceNetworkCoordinator.plan_claims` + `claim_many` 抢租约）。只有 `next_run_at` 到期的源才被 claim。

**阶段 2 · 抓取解析**（`github_releases.py:collect`）：带官方 header 请求 Releases API，逐条 `_to_article` 做确定性过滤（跳过 draft/prerelease/不稳定版本/无时间），生成 `ArticleRecord`，其中 `id = stable_id("github-release", url)`、`source_type_verified=True`、`tier="t1"`。

**阶段 3 · 合并去重**（`merge_by_url`）：按 URL 去重，官方优先。

**阶段 4 · 分发流水线**（`pipeline.py:run`）：
1. `is_distribution_eligible` → 直接通过（非混合源）。
2. `article_content_fingerprint` + `filter_changed` → 新内容进入。
3. `save_many` 持久化。
4. 预筛（可选）、分类摘要（可选）。
5. `score_articles`：authority=100（T1），LLM 打 novelty/impact/practicality。
6. `select_curated`：priority（score+质量调整）≥ threshold（60）→ 入选，受分类容量约束。

**阶段 5 · 回写健康**（`_refresh_source_health`）：更新 `next_run_at`、成功率、熔断状态。

**阶段 6 · 出现在精选流**（`v1_routes.py:list_items`）：`GET /api/v1/items?mode=selected` 读 `articles ⋈ curation_decisions where selected=true`，排序、keyset 分页、ETag。

# 第 5 章 数据库详解

## 5.1 表清单（SQLite，34 张表）

| 分组 | 表名 | 用途 |
|---|---|---|
| 采集/分发 | `articles` | 规范化文章（source_url 主键 + content_fingerprint） |
| | `sources` | 信源注册（含熔断/租约状态） |
| | `source_runs` | 每次抓取的结构化诊断 |
| | `curation_decisions` | 每篇文章的预计算精选决策 |
| 创作 | `tasks` / `evidence_packs` / `drafts` | 任务、证据包、草稿 |
| | `creator_projects` / `content_opportunities` | 创作项目、内容机会 |
| | `account_profiles` | 版本化账号画像 |
| 审计 | `prompt_versions` / `llm_call_records` / `creation_replay_reports` | 生成审计 |
| 日报 | `daily_reports` | 日报（date+revision 复合主键） |
| 精选镜像 | `selected_sync_items/changes/cursors/snapshots/snapshot_pages/state` | 双游标同步 |
| 评估 | `evaluation_*`（6 张） | 人工标注/评审/裁决 |
| Story | `stories` + `story_*`（7 张） | Story 影子 |
| 迁移 | `schema_migrations` | 迁移版本记录 |

## 5.2 schema 迁移机制

`schema_migrations` 表记录已应用版本。启动时 `_run_schema_migrations()` 按顺序执行 18 个迁移，每个在事务内 `CREATE/ALTER + INSERT version`。新增表用 `create(checkfirst=True)`；加列用 `ALTER TABLE ADD COLUMN` + `_has_column` 幂等判断；回填通过专门的迁移函数（如从 `source_metadata` 回填 `source_id`、按批次回填全局断网标记）。

**关键设计**：**时间字段全部用 String 存 UTC ISO-8601 字符串**（非 DateTime 列），枚举存 `.value` 字符串。这使加列/排序/跨库迁移成本低、无时区列类型耦合。

## 5.3 增量指纹 filter_changed

`SqliteArticleRepository.filter_changed()`：按 `source_url` 取存量 `content_fingerprint`，与新算的指纹比对，仅返回新 URL 或指纹变化项。指纹优先用 `ingestion_fingerprint`（采集器输入指纹），否则 sha256(title+summary)。**AI 富化（改 summary/category）不会改变指纹**——指纹在富化前就固定了。

## 5.4 精选镜像双游标

`domain/sync.py` + `SqliteSelectedSyncRepository`：

- `reconcile()`：对权威精选集做 diff，upsert 到 items（含 content_hash），每次变更 append 到 changes（自增 sequence）。
- `snapshot()`：冻结完整快照，分页 token + TTL（默认 900s）。
- `changes()`：按 sequence 增量拉取。
- 超 `max_changes`（默认 10000）时删旧并上移 `floor_sequence`，低于 floor 的游标触发 `SnapshotRequiredError`（客户端需重取快照）。

## 5.5 SQLite vs MongoDB

| 能力 | SQLite | MongoDB |
|---|---|---|
| Article/Curation/Task/Evidence/Draft | ✅ | ✅ |
| CreatorProject/AccountProfile/Opportunity/Audit | ✅ | ✅ |
| SelectedSync | ✅ | ✅ |
| Source/SourceRun/DailyReport | ✅ | ❌（内存降级） |
| Story 影子 | ✅ | ❌ |
| Evaluation 评估 | ✅ | ❌ |

**结论**：Mongo 是早期兼容分支，主路线是 SQLite。
