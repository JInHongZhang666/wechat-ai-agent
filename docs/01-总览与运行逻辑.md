## 第 1 章 项目总览

### 1.1 项目定位

这是一个**本地单进程的「AI 资讯采集—分发—创作」一体化智能体**。它共享同一套文章、评分和证据数据，同时服务两类对象：

- **信息读者**：自动采集公开 AI 资讯，去重、评分、精选后输出到资讯流 / 热榜 / 日报。
- **公众号创作者**：从精选 / 热文中选题，生成证据包 → 内容机会 → Content Brief → 初稿 → 质检 → 微信富文本导出。

一句话理解它：**把「公开数据自动采集 → 去重与热度评分 → 账号画像 → 内容机会评分 → 证据包 → Content Brief → 作者材料 → 研究初稿 → 质量检查 → 人工编辑 → 最终人工确认 → 微信富文本导出」接到一个可操作的网页里。**

### 1.2 核心设计哲学

全项目最核心的一句话，写在多个文件的注释里：

> **「能用代码就别用模型」**（can code, don't model）——精选决策是代码，模型只负责打分。

具体落地为三条铁律：

1. **决策权在代码手里**：LLM 只在「预筛、分类摘要、维度打分、成文、语义核查」等处出现，**唯独不在「是否精选」这个决策点**。精选是纯代码门槛，任何一次决策都能重放验证。
2. **不冒充 AI 成稿**：未配置 LLM 时走确定性规则回退，并在推荐理由 / 审计里**显式标注**「未用模型」，绝不把规则结果伪装成 AI 输出。
3. **确定性 / 可复现优先**：ID、指纹、决策、策略版本都是确定性的，服务重启后能从持久化数据精确重建。

### 1.3 技术栈

| 层 | 技术 |
|---|---|
| 语言 | Python 3.12+ |
| Web 框架 | FastAPI（Uvicorn，单 worker） |
| 数据校验 | Pydantic v2 |
| 存储 | SQLite（默认，SQLAlchemy 2.x Core）/ MongoDB（可选，motor） |
| 调度 | APScheduler |
| HTTP 客户端 | httpx |

| 前端 | React + TypeScript + Vite（产物由 FastAPI 直接托管） |

**分层原则**：`domain/ports.py` 用 `Protocol`（协议类）定义仓库接口，`storage/` 和 `collectors/` 是具体实现，`main.py` 负责装配（依赖注入）。这是典型的**端口与适配器（六边形）架构**——业务逻辑不依赖具体数据库或采集实现，为将来替换数据库预留了接口。

## 第 2 章 运行逻辑：从启动到产出的完整旅程

### 2.1 启动流程（`main.py:create_app`）

1. **解析数据库 URL**（`main.py:97`）：优先 `WECHAT_AGENT_DATABASE_URL`，默认 `sqlite:///:memory:`。启动脚本 `start.ps1` 会把它设为 `sqlite:///./data/wechat_agent.db`。
2. **lifespan 内先 `get_service()`**（`main.py:116`）：在接第一个请求**之前**就完成所有仓库构建和 schema 迁移（冷启动失败即报错，`fail-fast`）。这一步把重活从请求路径挪走，保证公开冷请求 SLA。
3. **启动后台采集调度器** `scheduler.start()`：每 1 分钟轮询一次到期信源。
4. **启动日报调度器** `scheduler.start_daily()`：上海时间每天 08:00 固化前一日日报。
5. **注册路由**：内部 `/api`、公开 `/api/v1`、`/feed` RSS、`/api/ops/*`（观测/评估/Story 影子）。
6. **HTTP 中间件**（`main.py:174`）：给每个请求生成 `requestId`、记录耗时、缓存命中、结果条数，回写 `X-Request-ID`、`X-Cache-Status`、`Server-Timing` 头。

### 2.2 后台采集循环

```
BackgroundScheduler(每 1 分钟)
   └→ create_scheduled_live_task()            # due_only=True, skip_if_none=True
        └→ _claim_source_ids()                # 决定本轮能跑哪些信源
             ├→ SourceNetworkCoordinator.plan_claims()  # 全局断网协调
             └→ source_repository.claim_many()          # 数据库租约，防并发
        └→ LiveRadarCollector.collect_sources()         # 8 线程并行抓取
             ├→ 7 天窗口抓取
             └→ 某类不足 5 条 → 自动扩到 30 天并报告真实缺口
        └→ pipeline.run(articles)             # 进分发流水线
        └→ _persist_source_runs()             # 写回每个信源的健康状态
```

**关键机制：租约 + 退避 + 熔断**（项目可靠性最重的一块）：

- 每个 `Source` 有持久化状态：`next_run_at`、`circuit_state`（CLOSED/OPEN/HALF_OPEN）、`consecutive_failures`、`success_rate_7d`。
- 采集前用 `claim_many` 抢租约（lease owner = task_id，15 分钟），防止同一信源被并发执行。
- 失败退避：指数退避 `schedule_minutes × 2^n`（封顶 12 小时）；429 遵守 `Retry-After`；永久 4xx 直接冷却 12 小时；连败 3 次熔断 OPEN。
- **批量级网络协调**（`services/source_network.py`）：把「单源故障」和「本机断网」分开——当一批里 ≥60% 信源同时报 `http_timeout/network_error` 时判定为全局断网，进入共享冷却，每批只探测 3 个，逐步恢复，避免所有信源同时反复半开。

### 2.3 分发流水线（`services/pipeline.py:run`）

这是全项目的**心脏**，一条同步链路：

```
原始文章
  → is_distribution_eligible()            # AI 相关性预筛（纯代码）
  → article_content_fingerprint()         # 算内容指纹
  → filter_changed()                      # 增量：未变化的内容直接跳过
  → save_many()                           # 先持久化原始文章
  → [Phase 1]  pre_screen（可选便宜模型）
  → [Phase 1.5] classify_and_summarize（分类 + 摘要）
  → [Phase 2]  score_articles（四维打分）
  → [Phase 3]  select_topics（5+5 选题）+ select_curated（代码精选）
  → [Phase 4]  _related_articles（同簇相关文章）
  → _save_curation_decisions()            # 写精选决策
  → _rebalance_recent_curation()          # 跨轮分类容量平衡
```

**增量处理的精髓**：RSS/API 会反复返回同一窗口的内容，所以**在花任何模型调用之前**先用指纹过滤未变化内容；预筛拒绝的文章下一轮也不会重复消耗模型。`DISTRIBUTION_STRATEGY_VERSION = "distribution-v3.2"` 是策略版本号——版本变化会**故意让缓存失效**，以便受控重放产生新决策。

### 2.4 评分与精选

**四维加权公式**（`scoring/heat.py`）：

```
Score = source_authority×0.30 + content_novelty×0.25
      + industry_impact×0.25 + practical_value×0.20
```

- **模型只打三个维度的分**（novelty / impact / practicality），`source_authority` 来自信源等级（T1=1.0 / T1.5=0.85 / T2=0.65，×100 得到 0–100 分）。
- **没有 LLM 时**走 `_deterministic_scoring`：固定内容分 + 小幅时效加成，并标记 `confidence=estimated`（离线估算），推荐理由里明确标注「未用模型」。
- **精选决策**（`scoring/curation.py`）完全确定性、可复现：门槛按等级（60 分）+ 分类调整 + 标题质量微调，再按**分类容量上限**（每类 6 条，论文 3 条）截取 Top N。

之所以把决策做成「可复现的代码」：同一套函数被采集、回填、Gold 集重放三处共用，任何一次决策都能被重新计算验证。

### 2.5 创作链路

```
精选文章 / 热门 / 粘贴链接（灵感）
  → build_evidence_pack()                # 证据包：区分已核实/冲突/待核实
  → build_opportunity()                  # 7 维加权 creationScore 内容机会
  → 版本化账号画像 AccountProfile          # 约束文风、栏目、禁用词
  → ContentBrief（证据门控的写作计划，章节绑定稳定 claim ID）
  → 三阶段成文：outline → section → editor
  → check_quality()                      # 8 类质量检查
  → 人工最终确认（固定确认语）→ finalize → 导出
```

**质量门是硬约束**：Brief 未过证据门不能生成正式研究稿；有确定性阻断项不能导出；自由编辑后**不会静默沿用旧质量结论**，会重新质检；LLM 缺位时生成的是**非阻断的人工复核审计项**，作者必须用固定确认语完成确认。

### 2.6 Agent 对话（M2，LangGraph）

`agent/graph.py` 实现真实的 **`decide → execute → decide` 循环**：

- 4 个本地工具：`search_ai_news`、`find_supporting_sources`、`build_research_evidence`、`refresh_news_sources`（+ AIHOT 扩展 `search_aihot_news`）。
- **硬约束**：最多 6 轮决策、8 次工具调用、120 秒超时、1200 输出 token；空查询是「真实观察结果」不伪造新闻；没有成功执行资讯查询不能标记 completed。
- **research 模式**：必须先用真实文章 ID 构建证据包，检查缺口（缺独立来源 / 缺一手来源 / 待核实 / 冲突），缺口未解决就返回 `needs_evidence`。
- **刷新工具**：服务端校验授权（只有 API 显式 `refresh_sources=true` 才允许），复用已有调度采集服务，不接受模型给的 URL。

### 2.7 数据流全景图

```
信源(33 配置/24 启用) → 采集器(8 线程) → 去重(URL 规范化 + 标题)
  → 相关性预筛 → 指纹增量 → 分类摘要 → 四维评分 → 代码精选
  → 持久化(Article + CurationDecision)
       ├→ 资讯流/热榜/日报(同一份数据源)
       ├→ 选题(5+5) → 证据包 → 机会 → Brief → 草稿 → 质检 → 导出
       └→ Agent 查询(读同一 eligible 池，不写库)
  → 采集后回写 SourceRun → 更新信源健康/退避/熔断
```
